# 03. 軟體（software）—— 說真話的程式碼

**我們主張：**

1. README（程式碼的門面說明）是一份承諾。程式碼兌現這份承諾，否則就修改 README。
2. 沒有測試（test，一段證明程式碼真的能運作的小檢查）背書的宣稱，只是謠言。
3. 每一個依賴（dependency，我們借來用的程式碼）都是一筆債，而每筆債我們都要交代清楚。
4. 我們寫程式碼，先給下一位讀的人看，其次才給機器跑。
5. 一個功能若隱瞞它真正在做的事，就是在說謊——即使沒有人寫下任何一句假話。

**要做：**

- 改變程式碼的行為時，在同一次修改裡同步更新 README。
- 先寫好測試，再宣稱功能可用。
- 每新增一個依賴，就在旁邊用一句白話寫清楚為什麼需要它。
- 命名要讓新來的人還沒打開檔案，就能猜到它是做什麼的。
- 把未完成的工作標示在使用者看得見的地方：「還沒做完」勝過一聲不吭。
- 讓錯誤訊息用白話說清楚發生了什麼事、接下來該怎麼辦。
- 刪掉我們不再維護的程式碼，別讓它留在原地腐爛。
- 每次發布（release，每一個我們交付的新版本）之前，把自己的 README 當成陌生人來讀一遍，修掉讓自己困惑的地方。

**不要做：**

- 不要推出一顆按了沒反應的按鈕。
- 不要把還在規劃中的功能描述得像已經存在。
- 不要在工作失敗或仍在執行時就顯示成功。
- 不要為了省下一個下午而加一個依賴，卻為它付出一整年。
- 清楚的程式碼能做到的事，就不要用賣弄聰明的程式碼來寫。
- 不要在任何地方印出機密（secret，例如密碼、金鑰）——只寫出存放機密的檔案名稱，絕不寫出機密本身。

**為什麼：**

軟體是唯一不用睡覺的工人。所以它一旦說謊，就是一天說上幾千次，對著無法反駁的人說。一份與程式碼不再相符的 README，教給每一位新讀者的都是假的東西。一個蓋在壞掉成果上的綠色勾勾，浪費的是每一個信任它的人的時間。我們讓程式碼保持誠實的方式，和我們讓金錢保持誠實的方式一樣：寫下每一個宣稱，檢驗每一個宣稱，而且任何人——不只是專家——都能沿著這條線索，從承諾一路追到證明。

**檢驗：**

如果一個陌生人先讀 README，再跑測試，最後讀程式碼——這三者說的是同一個故事嗎？
